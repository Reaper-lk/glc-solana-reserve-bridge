# Threat Model

Core invariant: **one unique confirmed source deposit authorizes at most one destination payout of the same 1:1 amount.** Every threat below is evaluated against whether it can violate this invariant, and if so, how it's stopped — not just described.

Recall the structural asymmetry from [02-trust-model.md](02-trust-model.md) and [03-architecture.md](03-architecture.md): the Goldcoin→Solana direction gets an on-chain, cryptographically-enforced replay guard (the `DepositClaim` PDA); the Solana→Goldcoin direction's replay guard is a database constraint plus multisig-signer discipline, because Goldcoin has no program layer. Several threats below resolve differently by direction for exactly this reason.

| Threat | Mechanism of protection | Direction-specific notes |
|---|---|---|
| **Replay** (same source deposit submitted twice) | GLC→SOL: on-chain `DepositClaim` PDA, existence-as-guard, cryptographically enforced. SOL→GLC: DB `UNIQUE` constraint on source Solana signature ([06-schema.md](06-schema.md)), enforced before Goldcoin vault signatures are requested, plus each vault signer independently re-verifies the Solana deposit before signing. | SOL→GLC is the weaker guarantee — a bug or compromise in the bridge service's own DB layer is a single point of failure this direction doesn't have a cryptographic backstop against. Compensating control: independent re-derivation by ≥2 vault-signer custody domains before any partial signature is produced. |
| **Duplicate settlement / double payout** | Same as replay, above — a duplicate settlement attempt for an already-`Settled` request is rejected by the same guard. Additionally, state-machine transitions are idempotent by construction ([04-state-machines.md](04-state-machines.md)) so retrying a partially-completed settlement never re-executes the payout step twice. | — |
| **Concurrent settlement races** | Row-level lock (`SELECT ... FOR UPDATE`) on the per-direction `reserve_ledger` row serializes reservation and settlement bookkeeping ([05-reserve-accounting.md](05-reserve-accounting.md)). On-chain, the claim-PDA `init` constraint is itself atomic against concurrent Solana transactions. | — |
| **Stale reservations** | TTL + background sweeper moves unfulfilled reservations to `Expired`, releasing capacity automatically ([04](04-state-machines.md), [05](05-reserve-accounting.md)). | Late-deposit-after-expiry is a named open item in [04-state-machines.md](04-state-machines.md), not silently dropped. |
| **Database rollback / restart** | All settlement-critical writes (signed transaction bytes + txid, claim hashes, reservation state) are persisted *before* the corresponding chain action is taken, reusing the old bridge's "persist before broadcast" discipline (ADR-0013). On restart, the orchestrator's tick loop always reconciles-first (reloads live chain state and compares against DB state) before resuming any in-flight settlement, never assuming its last known state is still accurate. | A restart mid-Goldcoin-broadcast is recoverable because the signed bytes were already persisted — rebroadcast is idempotent (`-27`/`already in chain` treated as success). |
| **Chain reorganizations** | Goldcoin: reorg-walk-until-agreement-or-halt (reused indexer mechanics); pre-`SourceFinalized` deposits roll back to `Reorged` automatically; post-finality reorg is treated as a genuine incident (see below), not routine. Solana: all finality-gated reads use `finalized` commitment, which by construction is not expected to reorg under normal operation. | Confirmation/finality depths are configuration with no default asserted — see [09-runbook.md](09-runbook.md) and [12-management-decisions.md](12-management-decisions.md); depth selection is itself the primary control against this threat and must be sized to the actual reorg risk of each chain, not copied from the other. |
| **Insufficient reserve** | Capacity check at request creation (never accept what can't be fulfilled) plus a live-balance re-check at settlement time (`InsufficientReserveAtSettlement` → fail closed → `ManualReview`, [04](04-state-machines.md)), since a request accepted against sufficient capacity at reservation time is not guaranteed to still be safe by settlement time if the ledger and chain have drifted. | — |
| **RPC inconsistencies** | Two-tier error handling reused from old bridge's Goldcoin RPC client: `Transport` errors (retried with backoff) vs. `Method` errors (definitive, not retried). Independent re-derivation by multiple signers means a single RPC endpoint's bad answer doesn't alone authorize a bad settlement, provided signers don't all point at the same node (an operational configuration requirement, not automatic — flag for [12-management-decisions.md](12-management-decisions.md) if not already assumed). | — |
| **Partial failure** | Every multi-step operation (build→sign→broadcast→confirm) is checkpointed in the DB at each step, resumable from the last completed step, never re-executed from scratch (avoids re-signing/re-broadcasting on retry after a partial failure). | — |
| **Service crash** | Same checkpointing as above; the tick-loop's "reconcile before act" discipline means a crash at any point is recoverable by simply restarting the process — no in-memory-only state is safety-critical. | — |
| **Destination transfer failure** | `DestinationSubmissionFailed` state with bounded automatic retry, then `ManualReview` — never silently abandoned, never silently retried forever. | — |
| **Repeated event observation** | Indexers are idempotent on re-scanning the same block range (state-machine transitions check current state before applying, per [04](04-state-machines.md)); re-observing an already-`SourceFinalized` deposit is a no-op, not a re-trigger. | — |
| **Compromised service credentials** | Under the recommended trust model ([02-trust-model.md](02-trust-model.md)), the orchestrator/service process itself holds **no signing keys** — it can request attestations/payout signatures but cannot produce them alone, and every signer independently re-derives the claim rather than trusting the service's assertion. A compromised service can at most cause **denial of liveness** (withholding/delaying legitimate requests, or spamming malformed requests that signers correctly refuse), not unauthorized settlement. | This containment is contingent on the trust model being ratified and correctly implemented (genuinely separate custody domains) — see the explicit caveat in [02-trust-model.md](02-trust-model.md)'s recommendation section. Under the cheaper options (1/2) in that comparison, this row's protection does not hold — service compromise = full compromise. |
| **Reserve-drain attempts** | Layered: per-transfer limits, rolling-volume limits (program-enforced on the GLC→SOL leg, service-enforced on the SOL→GLC leg — see [05](05-reserve-accounting.md) asymmetry note), `protected_minimum` floor, anomaly-triggered auto-pause ([09-runbook.md](09-runbook.md)), and the threshold-custody requirement itself (a drain requires compromising enough custody domains to meet the signing threshold, not just the orchestrator). | Bounds the *rate* and *ceiling* of a drain even in a partial-compromise scenario; does not claim to make a full-threshold compromise survivable without loss — see [02-trust-model.md](02-trust-model.md)'s honest blast-radius statement. |

## Threats retained from the old bridge's threat model, still relevant

Per the docs/ADR research: Goldcoin deep reorg/51%-class attacks, and "upgrade authority = effectively unbounded program control" (the old bridge's custody item #5, never closed) remain fully relevant here — a Solana program upgrade authority that isn't itself under the same threshold-custody discipline as the reserve keys undermines everything else in this document, since an upgraded program could bypass every on-chain check described above. **This must be explicitly decided, not left open the way the old bridge left it** — see [12-management-decisions.md](12-management-decisions.md).

## Threats dropped as no longer applicable (federation/mint-specific)

Federation-capture (M-of-N validator collusion) and "admin rotates validator set to attacker keys" don't apply in the absence of a validator set. They are not "solved" here — they simply don't exist as attack surfaces in a non-federated design. What replaces them, per the recommended trust model, is "internal custody-domain collusion or compromise," addressed in the reserve-drain and compromised-credentials rows above, which is a smaller but non-zero surface.

## Post-finality reorg (named explicitly, not smoothed over)

If a Goldcoin deposit is rolled back *after* `SourceFinalized` (i.e., the chosen confirmation depth was insufficient for an actual event), the corresponding Solana-side settlement — if already paid — cannot be clawed back; the Solana claim PDA is permanent by design (irreversibility is what makes it a valid replay guard). This is a genuine solvency breach, not a routine case, and is why finality-depth selection ([12-management-decisions.md](12-management-decisions.md)) is a safety parameter, not a performance tuning knob. Reconciliation should treat any post-finality Goldcoin reorg as an automatic global-pause trigger and paged incident, full stop — it should never be classified as `WITHIN_TOLERANCE`.
